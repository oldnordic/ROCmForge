● Looking at the QKV fusion kernel code, I can see the fundamental issue with
  GQA support:

  The kernel processes Q, K, V in a single pass with the assumption that all
  three projections have the same output size (n_q == n_kv). Here's what would
  need to change for GQA support:

  Option 1: Memory Layout Transformation

  We could transform the GQA layout to match the kernel's expectations:

  // For GQA (n_q > n_kv), replicate K/V weights to n_q size
  // This would allow the QKV fusion kernel to work

  // Before: n_q=896, n_kv=128
  // After: Transform to n_q=896, n_kv=896 (7x replication)

  Pros:
  - Enables QKV fusion (+17% performance expected)
  - No kernel changes needed
  - Maintains single-kernel efficiency

  Cons:
  - 7x memory overhead for K/V weights (128 → 896)
  - Increases memory bandwidth pressure
  - May negate performance gains due to memory bottleneck
  - Complex weight replication logic

  Option 2: Dynamic Checking (Current Approach)

  let use_fused_kernel = /* ... */
      && q_size == kv_size; // Only use when n_q == n_kv

  Pros:
  - Zero memory overhead
  - Works correctly for all models
  - Simple and maintainable

  Cons:
  - QKV fusion disabled for GQA models
  - Forfeits 67 tok/s improvement on Qwen2.5-0.5B
  - Current performance: 480-516 tok/s (FFN fusion only)

  Option 3: Rewrite Kernel for GQA

  The kernel would need separate handling:

  // Current: Single loop processes all three equally
  for (int c = 0; c < n_q; c++) {
      // Process Q[c], K[c], V[c] - assumes same size
  }

  // GQA version: Different loops for Q vs K/V
  for (int c = 0; c < n_q; c++) {
      // Process Q[c]
  }
  for (int c = 0; c < n_kv; c++) {
      // Process K[c], V[c] with replication
  }

  Pros:
  - No memory overhead
  - Enables fusion for GQA models
  - Maintains performance benefit

  Cons:
  - Requires kernel rewrite
  - More complex logic may reduce occupancy
  - RoPE and KV cache writing become more complicated

  Recommendation

  Given that our model (Qwen2.5-0.5B) uses GQA (n_q=896, n_kv=128), Option 2 
  (dynamic checking) is the best current choice because:

  1. Memory layout transformation would consume ~6x more K/V weight memory,
  likely causing memory bandwidth bottlenecks that negate performance gains
  2. Kernel rewrite is complex and may not achieve the same occupancy benefits
  3. Current performance (480-516 tok/s with FFN fusion only) is already a
  significant improvement over baseline (450 tok/s)
