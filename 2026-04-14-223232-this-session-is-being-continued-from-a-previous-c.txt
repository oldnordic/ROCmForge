● Analysis Complete: Q6_K Graph Compatibility

  After reading AMD's official HIP graph documentation from
  /home/feanor/Projects/rocm-examples/ and ROCm online docs, here's what I
  found:

  The Real Issue: Architecture, Not Fundamental Incompatibility

  You were absolutely right. The problem is NOT that Q6_K is "fundamentally
  incompatible" with HIP graphs. The problem is that Q6_K was never architected 
  correctly to be graph-compatible.

  Key Findings

  AMD's Example Kernels (All Graph-Compatible):
  - Very simple main kernels with straightforward operations
  - Grid-stride loops with simple arithmetic
  - No complex bit manipulation in main kernel
  - Either no device functions OR device functions handle all complexity

  Our Q4_K Kernel (Works with Graphs):
  __device__ inline float vec_dot_q4_k(...) {
      // ALL dequantization complexity here
      // Bit manipulation, scales, indexing
  }

  __global__ void gemv_q4_k_f32_kernel(...) {
      // SIMPLE main kernel - just loops and calls device function
      sum += vec_dot_q4_k(...);
  }

  Our Q6_K Kernel (Fails Graph Capture):
  __global__ void gemv_q6_k_f32_kernel(...) {
      // EVERYTHING inline - no device function
      // Complex bit manipulation inline
      // Complex indexing calculations inline
      // Type punning with memcpy inline
      // Nested loops with data-dependent logic
  }

  The HIP Graph Capture Constraint

  Error code 3: hipGraphInstantiateNodeOperationNotSupported means:
  - ❌ NOT: "This quantization format is incompatible"
  - ❌ NOT: "Q6_K can never work with graphs"
  - ✅ YES: "This specific kernel implementation uses operations not supported
  in graph nodes"

  The main kernel is too complex. HIP graph capture wants simple main kernels.

  Refactoring Strategy

  Follow the Q4_K pattern (which is exactly what llama.cpp does):

  1. Create vec_dot_q6_k device function - Move ALL dequantization logic there
  2. Simplify main kernel - Just loop over blocks and call device function
  3. Test with safety features - Use our temperature monitoring, GPU reset
  prevention
  4. Enable graph capture - Remove Q6_K from decode_graph_disabled()

  Expected Performance Impact

  If Q6_K can use HIP graphs like Q4_K:
  - Current: 134 tok/s (without graphs)
  - Potential: 300-500 tok/s (with graphs, based on Q4_K's 527 tok/s)
  - Improvement: 2.2-3.7x faster

  This would dramatically close the 3.9x performance gap to Q4_K.
